# Design — Ironwood (NU6.3) receive/sync support in the SDK

**Date:** 2026-06-30
**Branch:** work directly on the **current** branch `michal/MOB-1455-ironwood-migration-prototype-ffi`
(the FFI/welding base). The work lands as several small, logically-scoped commits (see §9) so the branch
can later be split into smaller stacked PRs.
**Ticket:** MOB-1455 (Ironwood sync).

## 1. Context & findings (verified)

"Ironwood" is **not a new shielded pool** — it is **Orchard note-version V3**. It reuses Orchard's
circuit, IVK/FVK, `orchard::Note`, nullifier, and `MerkleHashOrchard` commitment, and is **received at
the existing Orchard receiver of a unified address** (there is *no* separate Ironwood address/receiver).
The only Ironwood-specific machinery is bookkeeping layered on Orchard: a separate commitment tree, a
`note_version` discriminator, a separate balance line, the NU6.3 consensus branch, and a second
transaction bundle. In one sentence: **scanning Ironwood = "Orchard scanning, run a second time" with
the same keys.**

The pinned **valargroup `librustzcash` fork fully implements Ironwood receiving/scanning** (live in the
SDK build via `zcash_unstable="nu6.3"`): compact `ironwoodActions` ingestion → trial-decrypt with the
Orchard IVK → store in `orchard_received_notes` (`note_version=3`) → a dedicated `ironwood_tree_*`
shardtree + `put_ironwood_subtree_roots` → a distinct `AccountBalance::ironwood_balance`.

**What's missing for the SDK to sync Ironwood:**
1. The SDK's `libzcashlc` (`rust/src/`) does not expose the fork's Ironwood functions/fields.
2. The Swift layer has no Ironwood balance, subtree-root fetch, tree-state/checkpoint plumbing.
3. The lightwalletd proto the SDK uses lacks `ShieldedProtocol.Ironwood` / `TreeState.ironwoodTree`
   (and `CompactTx.ironwoodActions` / `ChainMetadata.ironwoodCommitmentTreeSize`).
4. **External blockers (confirmed, out of our control):** no lightwalletd serves Ironwood data today,
   and NU6.3's consensus branch ID is still a placeholder (`0xffff_ffff`) — it is on no network.

## 2. Goal & scope

**Goal:** make the SDK **Ironwood-ready** — wire the full receive/scan/balance path against the fork's
existing capability — so the SDK begins detecting Ironwood notes and reporting Ironwood balance the
moment a lightwalletd serves the data and NU6.3 activates. No app-facing behavior changes until then.

**In scope:** receiving + scanning Ironwood notes; maintaining the Ironwood commitment tree (subtree
roots + tree state); reporting Ironwood balance in `AccountBalance`/`WalletSummary`; the proto, FFI,
welding, sync-pipeline, and checkpoint plumbing to support all of the above.

**Out of scope (explicit):**
- **Spending Ironwood notes** (proposals/note-selection/PCZT that *spend* V3 notes) — a separate,
  larger surface; the migration already covers the only near-term Ironwood-output case. Deferred.
- **A new Ironwood receiver/address** — does not exist by design; funds land at the Orchard receiver.
- **Closure/Combine adapter or public `Synchronizer` API changes** — balance flows through the existing
  `AccountBalance` surface; no new public methods are required for receive/scan.

**Public API impact:** the one public-surface change is **additive** — `AccountBalance` gains a public
`ironwoodBalance: PoolBalance` field (always `.zero` until NU6.3 is live). This is a public type change
(new field, and its memberwise init signature), so per §10 a ZODL handoff is produced when the work is
done.

## 3. Approach

Treat Ironwood as a **parallel line item next to Orchard** everywhere Orchard already appears, mirroring
the fork's own model. This is the most faithful and least surprising structure, and it makes each new
piece a near-mechanical copy of its Orchard analog.

Considered and rejected: a *passthrough-minimal* variant that relies on SwiftProtobuf unknown-field
preservation to carry `ironwoodActions` to Rust and skips the compact-format proto change. It "works"
for the scan path (verified: `ZcashCompactBlock.data = compactBlock.serializedData()` preserves unknown
fields), but it is implicit, leaves block-metadata counters ignoring Ironwood, and is not the "full
plumbing" outcome chosen. We make the wire explicit instead — while noting passthrough as the safety net.

## 4. The work, by layer

### 4a. Proto / wire (`Modules/Service/GRPC/ProtoBuf/proto/` → regenerate)
**Toolchain resolved:** `protoc` (libprotoc 35.1) + `protoc-gen-swift` **1.35.1** (matches the pinned
`swift-protobuf` runtime) on PATH. `protoc-gen-grpc-swift` is **not needed** — these are message/enum
field additions only (no RPC change), so only `*.pb.swift` regenerate, not `*.grpc.swift`.

The checked-in stubs are stale (generated by a much older swift-protobuf than the pinned runtime), so
per the approved decision the two touched stubs are handled in **two commits** (see §9.1–9.2): (i)
regenerate `service.pb.swift` + `compact_formats.pb.swift` as-is with 1.35.1 — mechanical modernization,
no `.proto` change; then (ii) add the Ironwood fields on that baseline. Additions, matching valargroup's
field numbers exactly (wire-compat):
- `service.proto`: `ShieldedProtocol.ironwood` (= 2); `TreeState.ironwoodTree` (new field). **Mandatory**
  — Swift constructs `GetSubtreeRootsArg(shieldedProtocol: .ironwood)` and reads/forwards `TreeState`.
- `compact_formats.proto`: `CompactTx.ironwoodActions` (field 9, type `CompactOrchardAction`);
  `ChainMetadata.ironwoodCommitmentTreeSize`. Lets metadata count Ironwood and makes the wire explicit.

### 4b. FFI (`rust/src/`)
Mirror the Orchard FFI (targets identified):
- `lib.rs`: add `zcashlc_put_ironwood_subtree_roots` (copy of `zcashlc_put_orchard_subtree_roots:1482`,
  calling the fork's `db_data.put_ironwood_subtree_roots`).
- `ffi.rs`: extend the wallet-summary structs — add `ironwood_balance: Balance` (next to
  `orchard_balance:347/364`, sourced from `balance.ironwood_balance()`) and `next_ironwood_subtree_index`
  (next to `next_orchard_subtree_index:416/455/468`); populate them in `zcashlc_get_wallet_summary:1649`.
- cbindgen regenerates `libzcashlc.h` on build; the `rerun-if-changed` for changed rust files already
  exists. Scanning itself needs **no** new FFI: `zcashlc_scan_blocks` already forwards the serialized
  `TreeState` (now carrying `ironwoodTree`) and the fork scans `ironwood_actions` internally.

### 4c. Swift welding (`Rust/`, `Model/`, `Error/`)
- `ZcashRustBackendWelding` + `ZcashRustBackend`: add `putIronwoodSubtreeRoots(startIndex:roots:)`
  (mirror `putOrchardSubtreeRoots`).
- `Model/WalletSummary.swift`: `AccountBalance.ironwoodBalance: PoolBalance` +
  `WalletSummary.nextIronwoodSubtreeIndex: UInt32`; map them in `getWalletSummary`'s FFI→Swift
  conversion (`toAccountBalance()` / the summary mapping).
- Error codes (Sourcery): `rustPutIronwoodSubtreeRootsAllocationProblem` + `rustPutIronwoodSubtreeRoots`
  (next free ZRUST, ≈`ZRUST0109/0110`); regenerate `ZcashError*.swift`. Regenerate `AutoMockable`.

### 4d. Sync pipeline (`Block/`)
- `UpdateSubtreeRootsAction`: after the Orchard fetch, add a third fetch
  (`GetSubtreeRootsArg(shieldedProtocol: .ironwood)`) → `putIronwoodSubtreeRoots`, mirroring the
  Sapling→Orchard sequence. Add `compactBlockProcessorPutIronwoodSubtreeRoots` error code (next ZCBPEO).
- (Optional/cosmetic) extend `ZcashCompactBlock.Meta`/`outputCount` to also count `ironwoodActions`.

### 4e. Checkpoints & TreeState (`Checkpoint/`)
- `Checkpoint.swift`: add `ironwoodTree: String?` (optional, like `orchardTree`); decode it; include it
  in `treeState()` → `TreeState.ironwoodTree`. All current checkpoint JSONs are pre-NU6.3, so
  `ironwoodTree` stays `nil` everywhere for now (exactly how `orchardTree` is nil pre-NU5). The
  checkpoint-generation tooling will populate it once NU6.3 trees exist.

## 5. Verification strategy (honest about the blocker)

With **no lightwalletd serving Ironwood** and **NU6.3 unfinalized**, end-to-end "real note scans into
balance" **cannot be verified** and is the headline deferral. What we *can* and *will* verify
(OfflineTests + a local-FFI macOS rebuild, the path already used for the migration work):
- **FFI round-trips:** `getWalletSummary` on an empty/test wallet returns `ironwoodBalance == .zero`
  without crashing; `putIronwoodSubtreeRoots` with sample roots against a test DB succeeds (mirrors any
  existing orchard subtree-root test).
- **Swift decode/mapping:** `AccountBalance` exposes `ironwoodBalance`; `WalletSummary` exposes
  `nextIronwoodSubtreeIndex`; `Checkpoint` decodes `ironwoodTree`; `TreeState` carries it.
- **Pipeline:** `UpdateSubtreeRootsAction` fetches Ironwood roots from a **mocked** service and calls
  `putIronwoodSubtreeRoots` (mirror the existing action test).
- **Proto:** a `CompactTx` round-trips `ironwoodActions`; `ShieldedProtocol.ironwood` exists.
- **Build:** local-FFI macOS slice rebuilds; full `OfflineTests` green; SwiftLint clean.

**Cannot verify (deferred → final report):** real Ironwood note detection, balance accrual from a chain,
lightwalletd actually serving the fields, and any NU6.3-activation behavior. A future darksidewalletd
fixture (feeding synthetic `ironwoodActions`) is the eventual integration-test path, but it itself needs
NU6.3 plumbing and is out of scope here.

## 6. Risks & deferred items (→ carried to final report)

- **External blockers:** lightwalletd serving Ironwood; finalized NU6.3 branch ID. Until both land, this
  is dormant plumbing — correct by construction/mirroring, but unexercised on real data.
- **Moving target:** NU6.3 / the valargroup fork are pre-release; field numbers or APIs could shift. We
  pin to the fork as it is today and flag any churn.
- **Proto toolchain:** RESOLVED — `protoc` 35.1 + `protoc-gen-swift` 1.35.1 on PATH; only `.pb.swift`
  regenerate (no RPC change). The stale-generator skew is absorbed by the isolated mechanical regen
  commit (§9.1), keeping the Ironwood diff clean.
- **FFI ABI change:** extending the wallet-summary C structs requires a local-FFI rebuild + header
  regen; multi-arch xcframework (`init-local-ffi.sh`) recommended before any PR (macOS slice verified
  here).
- **Spending Ironwood** and **app-facing surfacing of Ironwood balance** (if the app wants it shown
  separately rather than folded into the Orchard line) are follow-ups.

## 9. Delivery — small, logically-scoped commits (for later PR splitting)

All work stays on the current branch `michal/MOB-1455-ironwood-migration-prototype-ffi`, but is committed
as a sequence of small, self-contained commits so the branch can later be cut into smaller (stacked)
PRs. The commits are ordered bottom-up (each builds on the previous; **each must leave the build green +
OfflineTests passing**, so any prefix can become a PR). Each commit message is `[MOB-1455] <title>`.

1. **proto regen (mechanical)** — regenerate `service.pb.swift` + `compact_formats.pb.swift` with the
   pinned `protoc-gen-swift` 1.35.1, **no `.proto` change**. Pure modernization that resolves the stale
   generator/runtime skew; isolated so the next commit stays a clean Ironwood-only diff.
2. **proto: Ironwood fields** — add `ShieldedProtocol.ironwood` + `TreeState.ironwoodTree` to
   `service.proto` and `CompactTx.ironwoodActions` + `ChainMetadata.ironwoodCommitmentTreeSize` to
   `compact_formats.proto`; regenerate. Small clean diff on the modernized baseline. (Wire readiness.)
3. **ffi** — `zcashlc_put_ironwood_subtree_roots` + `ironwood_balance`/`next_ironwood_subtree_index` in
   the wallet-summary FFI structs (`rust/src/lib.rs`, `rust/src/ffi.rs`); regenerated `libzcashlc.h`.
4. **welding + models** — `putIronwoodSubtreeRoots` welding, `AccountBalance.ironwoodBalance` +
   `WalletSummary.nextIronwoodSubtreeIndex` mapping, new ZRUST error codes (+ generated error files),
   `AutoMockable` regen, and the FFI/model OfflineTests.
5. **sync pipeline** — `UpdateSubtreeRootsAction` Ironwood fetch (+ ZCBPEO error code) and its test.
6. **checkpoints** — `Checkpoint.ironwoodTree` decode/`treeState()` plumbing and its test.
7. **docs** — `CHANGELOG.md`, `MIGRATING.md`, and the ZODL handoff (§10).

I'll commit only when each unit is green; I won't push or open PRs (that stays your call, as before).
